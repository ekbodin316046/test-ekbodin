# 05 — บันทึกการตัดสินใจ

รูปแบบ ADR ย่อ: บริบท → ตัดสินใจ → ทางเลือกที่ไม่ได้เลือก → สิ่งที่ต้องแลก

---

## ADR-01 ตัด `Amount (decimal)` ออกจากโมเดล

**บริบท** โครงร่าง schema ตอนแรกมี `Amount (decimal)` กำกับว่าเป็นคอลัมน์ `เหตุผล/xxxxx`
แต่ในภาพข้อสอบไม่มีคอลัมน์จำนวนเงิน คอลัมน์ที่สามคือ `เหตุผล` แสดงข้อความ `xxxxx`

**ตัดสินใจ** ไม่มี `Amount` ในระบบ ใช้ `Reason nvarchar(500)`

**ไม่ได้เลือก** เก็บ `Amount` ไว้ในฐานข้อมูลแต่ไม่แสดง — ทำให้มีคอลัมน์ที่ไม่มีใครใช้
และเป็นสัญญาณว่าอ่านโจทย์ไม่ครบ

**แลก** ถ้าโจทย์จริงต้องการจำนวนเงินจะต้องเพิ่ม migration ใหม่ ซึ่งเป็นงานเล็ก

## ADR-02 `Documents.Reason` เก็บค่าซ้ำกับ `ApprovalLog`

**บริบท** ภาพ IT 03-1 แสดงเหตุผลทุกแถว รวมแถวที่ยังรออนุมัติซึ่งไม่มีประวัติการอนุมัติ

**ตัดสินใจ** `Documents.Reason` เป็นเหตุผลปัจจุบัน seed ให้ครบทั้ง 10 แถว
เวลาตัดสินใจจะเขียน `ApprovalLog` และทับ `Documents.Reason` พร้อมกัน

**ไม่ได้เลือก**
- ดึงเหตุผลจาก `ApprovalLog` ล่าสุดเสมอ — แถวรออนุมัติจะว่าง ไม่ตรงภาพ และต้อง join ทุกครั้ง
- เก็บเฉพาะใน `Documents` ไม่ต้องมี `ApprovalLog` — เสียประวัติ ซึ่งเป็นส่วนที่ทำให้งานดูจริงจัง

**แลก** ข้อมูลซ้ำสองที่ คุมด้วยการเขียนทั้งคู่ใน method เดียวภายใน transaction เดียว
จึงไม่มีทางไม่ตรงกัน

## ADR-03 กฎ "ห้ามดำเนินการซ้ำ" อยู่บน entity

**บริบท** ข้อกำหนดหลักของข้อสอบ วางได้หลายที่: UI, controller, handler, entity

**ตัดสินใจ** อยู่ใน `Document.ChangeStatus` บน entity ใน `Domain`

**ไม่ได้เลือก**
- ตรวจใน UI อย่างเดียว — ยิง API ตรงก็ข้ามได้
- ตรวจใน handler — ถ้ามี use case ใหม่ต้องจำไปเขียนซ้ำ

**แลก** ไม่มีข้อเสียที่สำคัญ ได้ประโยชน์ตรงที่เทสได้โดยไม่ต้องมีฐานข้อมูล

## ADR-04 SQLite

**บริบท** คนตรวจต้องเปิดดูตารางได้ง่าย และควรรันได้โดยไม่ติดตั้งอะไรเพิ่ม

**ตัดสินใจ** SQLite ผ่าน EF Core ส่งมอบทั้ง `app.db`, `schema.sql`, `seed.sql`

**ไม่ได้เลือก** SQL Server LocalDB (ต้องมีติดตั้ง), SQL Server ใน Docker (ต้องมี Docker
และ image ใหญ่), PostgreSQL (ต้องติดตั้ง server และเครื่องมือดูตาราง)

**แลก** ไม่ใช่ฐานข้อมูลระดับองค์กร ชดเชยด้วยการเข้าถึงผ่าน EF Core ทั้งหมด
ไม่มี SQL ดิบผูก provider การย้ายไป SQL Server คือเปลี่ยนบรรทัดเดียวและสร้าง migration ใหม่

## ADR-05 MediatR 12.5.0 ไม่ใช่เวอร์ชันล่าสุด

**บริบท** MediatR ตั้งแต่ v13 เปลี่ยนไปใช้สัญญาอนุญาตเชิงพาณิชย์ v12.5.0 เป็นรุ่นสุดท้าย
ที่เป็น Apache-2.0

**ตัดสินใจ** ตรึงไว้ที่ 12.5.0

**ไม่ได้เลือก** ใช้ v14 ล่าสุด — เปิดคำถามเรื่องสัญญาอนุญาตในงานที่ส่งให้บริษัทดู

**แลก** ไม่ได้ฟีเจอร์ใหม่ ซึ่งงานขนาดนี้ไม่ได้ใช้อยู่แล้ว

## ADR-06 API รับ `documentIds` เป็น array

**บริบท** UI เลือกได้หลายแถวแล้วกดปุ่มเดียว

**ตัดสินใจ** endpoint เดียวรับหลาย id ทำใน transaction เดียว ถ้าใบใดผิดกฎยกเลิกทั้งชุด

**ไม่ได้เลือก** ยิงทีละใบจาก frontend — เกิดสถานะครึ่ง ๆ กลาง ๆ เมื่อใบกลางล้มเหลว

**แลก** ผู้ใช้ที่เลือกมา 10 ใบแล้วมีใบเสียใบเดียวจะไม่ได้อะไรเลย ซึ่งถูกต้องกว่า
การอนุมัติไปบางส่วนโดยไม่ได้สั่ง ข้อความ error ระบุชื่อเอกสารที่เป็นสาเหตุ

## ADR-07 ไม่ทำระบบเข้าสู่ระบบ

**บริบท** ข้อสอบไม่ได้ขอ แต่ `ApprovalLog.ActionBy` ต้องมีค่า

**ตัดสินใจ** `ICurrentUserAccessor` อ่าน header `X-User` ถ้าไม่ส่งมาใช้ `demo.user`

**ไม่ได้เลือก** hardcode ชื่อผู้ใช้ในหลาย ๆ ที่ — ทำให้ไม่มีจุดต่อชัดเจนเมื่อจะเพิ่ม auth จริง

**แลก** ไม่มีความปลอดภัยจริง ซึ่งอยู่นอกขอบเขตที่โจทย์กำหนด

## ADR-08 ธีมแบบ SLCM แทนสีใน mockup

**บริบท** mockup เป็น wireframe หัวเขียวตารางฟ้า สื่อโครงสร้างมากกว่าธีมสี

**ตัดสินใจ** ทำพฤติกรรมและโครงตารางตาม mockup ทุกจุด แต่ใช้ชุดสีและตัวอักษรเดียวกับ
ระบบ SLCM (`#492C79`, ฟอนต์ Prompt, เมนูข้าง 260px) พร้อมเมนูด้านข้าง

**ไม่ได้เลือก** ลอกสีเขียว/ฟ้าใน mockup ตรงตัว — ได้หน้าตาแบบ prototype ไม่เหมือนระบบจริง

**แลก** ต่างจากภาพในข้อสอบเรื่องสี จึงบันทึกการเทียบ mockup กับของจริงไว้ที่
[04-ui-ux](04-ui-ux.md) ให้ตรวจสอบได้ว่าไม่ได้ตกข้อกำหนดข้อใด

## ADR-09 เขียน CSS เอง ไม่ใช้ component library

**บริบท** ต้องคุมหน้าตาให้ตรง mockup และมีเวลาจำกัด

**ตัดสินใจ** CSS ของตัวเอง ใช้ CSS custom properties เป็น design token

**ไม่ได้เลือก** Angular Material (ต้องตั้ง theme และ override เยอะเพื่อให้ได้ตารางแบบนี้),
Bootstrap (ดึงมาทั้งชุดเพื่อใช้ไม่กี่ class)

**แลก** ไม่ได้ component สำเร็จรูป แต่ทั้งงานมีแค่ตารางและ modal สองแบบ

## ADR-10 เมนูข้างทุกอันต้องกดได้จริง

**บริบท** โจทย์มีหน้าเดียว แต่เมนูข้างที่มีลิงก์เดียวดูแปลก

**ตัดสินใจ** เพิ่มสองหน้าที่ทำงานจริงจากข้อมูลชุดเดิม — สรุปสถานะเอกสาร (คำนวณจาก
endpoint เดิม ไม่เพิ่ม API) และข้อมูลสถานะเอกสาร (ตารางหลัก)

**ไม่ได้เลือก** ใส่เมนูที่กดแล้วไม่มีอะไร — คนตรวจกดแล้วเจอหน้าเปล่าเสียคะแนนมากกว่าไม่ใส่

**แลก** งานเพิ่มเล็กน้อย (หนึ่ง endpoint และสอง component สั้น ๆ)

## ADR-11 คอลัมน์ audit หกตัวทุกตาราง และตั้งชื่อแบบ snake_case

**บริบท** ฐานข้อมูลจริงของระบบใช้มาตรฐานเดียวกันทุกตาราง — ชื่อคอลัมน์ `snake_case`
และมี `created_by` / `created_date` / `created_program` / `updated_by` / `updated_date` /
`updated_program` เป็น `varchar(50) NOT NULL` ครบทุกแฟ้ม โครงเดิมของงานนี้ตั้งชื่อแบบ
PascalCase และมีแค่ `CreatedAt` / `UpdatedAt` เฉพาะตารางเอกสาร

**ตัดสินใจ** ยกทั้ง schema ไปใช้มาตรฐานเดียวกับระบบจริง

- ตาราง `documents`, `document_status`, `approval_log` คอลัมน์ `snake_case` ทั้งหมด
- คอลัมน์ audit หกตัวครบทุกตาราง รวมไว้ที่ `AuditableEntity` และ `HasAuditColumns()`
- `created_program` เก็บรหัสหน้าจอ (`IT03`) อ่านจาก header `X-Program` เหมือนที่ ADR-07
  ทำกับผู้ใช้ ข้อมูลจาก seeder ใช้ `SYSTEM` / `SEED`
- คอลัมน์เดิมที่ความหมายซ้ำถูกยุบ — `CreatedAt`/`UpdatedAt` กลายเป็น `created_date`/
  `updated_date` ส่วน `ActionBy`/`ActionAt` ของ `approval_log` กลายเป็น `created_by`/
  `created_date` เพราะตารางนี้เขียนครั้งเดียวไม่แก้อีก คนสร้างแถวคือคนที่กดอนุมัติอยู่แล้ว

**ไม่ได้เลือก**

- เพิ่มคอลัมน์ audit แต่คงชื่อเดิมเป็น PascalCase — ได้ schema ที่ปนสองแบบในตารางเดียว
  ซึ่งอ่านแล้วเหมือนทำครึ่ง ๆ กลาง ๆ
- เก็บ `ActionBy` ไว้คู่กับ `created_by` — สองคอลัมน์ที่มีค่าเท่ากันเสมอ ขัดกับเหตุผล
  ที่ ADR-01 ตัด `Amount` ทิ้งไป
- ให้ handler เซ็ตค่า audit เอง — ลืมเมื่อไหร่ก็ได้แถวที่ไม่มีประวัติ จึงดักที่
  `SaveChangesAsync` ชั้นเดียวแทน

**แลก** ต้องสร้าง migration ใหม่ทั้งก้อนแทนการ alter ทีละคอลัมน์ และ `db/app.db` ต้อง
generate ใหม่ ยอมรับได้เพราะเป็นฐานข้อมูล mockup ไม่มีข้อมูลจริงให้รักษา

สัญญาของ API ไม่เปลี่ยน — JSON ยังส่ง `actionBy` / `createdAt` เหมือนเดิม เพราะเป็นชื่อ
ที่สื่อความหมายทางธุรกิจบนหน้าจอ ไม่ใช่ชื่อที่เก็บในฐานข้อมูล ฝั่ง Angular จึงไม่ต้องแก้
